Portage des methodes FV2 vers **Virtua Fighter 3 Team Battle** (`vf3tb`, Step 1.0), commence le 2026-08-21. **Le fait central, mesure et non suppose : VF3 n'est pas compresse.** La CROM contient 1685 `blr` et le menu de test en clair, la ou celle de FV2 n'a que 24 `blr` d'amorcage (voir [[project_fv2_mod]]). Le boot recopie le programme **octet pour octet** : RAM `0x000000-0x09FFFF` est identique a **100 %** a la CROM `0x110000-0x1AFFFF` (640 Ko), premier ecart pile a la fin. Adresse ROM = adresse RAM + `0xFFF10000`. Consequences : Ghidra peut travailler sur le zip seul (`crom.py` sort `vf3tb_program.bin`, base 0), et **un patch ROM permanent est possible** — ce que FV2 n'a jamais permis.

Deux differences de structure qui cassent le portage direct des outils FV2 :
- **Les tables du menu de test font 8 octets** (pointeur libelle + placement ligne/colonne, fin `FFFFFFFF FFFFFFFF`), pas 0x20 avec l'adresse de la variable en +0x0C. **Zero symbole gratuit** contre 56 chez FV2 : `symbols.py` ne se porte pas, remplace par `menus.py` (5 tables, 72 entrees, `vf3_menus.csv`).
- **Les reglages ne sont pas en RAM principale mais en backup RAM**, lus par `lwbrx` (routine d'affichage `0x00041EA8`, lecture du pays `0x0004217C`, table des libelles JAPAN/U.S.A./EXPORT/ASIA `0x00042CF8`). Ecrire le pays en RAM comme chez FV2 ne sert a rien.

**Pays : `0xF00DE01D`** (offset 0x1E01D de la backup RAM), 0 JAPAN, 1 U.S.A., 2 EXPORT, 3 ASIA. Trouve le 2026-08-21 : un seul octet bouge sur un appui TEST dans GAME ASSIGNMENTS ; verifie dans les deux sens, et la valeur redescend dans `NVRAM/vf3tb.nv`. Bloc des reglages a `0xF00DE000`, 4 octets par entree (2 derniers = `31 2E`), sauf ENERGY MAX en mot de 32 bits. Outil : `pays.py` + lanceur `VF3 - Choisir le pays.cmd`, qui travaillent sur le fichier NVRAM **jeu ferme**. Trois pieges : la page du menu ne se redessine qu'a l'entree ou sur changement (ecrire pendant l'affichage ne change rien a l'ecran) ; le pays est modifiable dans le menu chez VF3, contrairement a FV2 ; la NVRAM n'est ecrite qu'a la sortie propre.

**La cle de lecture du code : `r13 = 0x00108000`**, base du small data area de l'EABI PowerPC, posee par l'amorce a `0x00001540` (pile a `0x001EFFC0`). VF3 y range tous ses globaux, donc **aucune adresse absolue n'apparait dans le code** : chercher un `lis`/`addi` vers une variable ne donne rien, il faut chercher `offset(r13)` avec `offset = adresse - 0x108000`.

Resultat negatif utile : l'equipe validee n'existe **nulle part** en RAM sous la forme des identifiants choisis (fouille des 8 Mo en octets, demi-mots et mots, tous pas de 1 a 0x800). Le jeu convertit a la validation. Le curseur n'est reference par aucun `lbz 0x45(r13)` : il est vraisemblablement lu par acces indexe (`lbzx`), comme un tableau `curseur[joueur]`.

**Journal de modes VF3 : FAIT et tranche (2026-08-22).** Trouve par le code : la routine de debug en `0x00020C0C` fait `lbz r3,-0x5ff8(r13)` puis indexe la table de pointeurs des 59 noms en `0x0002B28C`. **DEUX niveaux :** `0x00102008` = mode (indice absolu), `0x00102009` = **sous-etat RELATIF au groupe**, `0x00102000` = drapeaux qui designent le groupe. La routine teste `andis. 0x3000` -> groupe attract (table `0x0002B344`, indice 46), `0x0300` -> combat (`0x0002B2E4`, indice 22), `0x0C00` -> selection (`0x0002B330`, indice 41), puis `lbz r3,-0x5ff7(r13)` et `lwzx`. Drapeaux observes : 0x10000000 attract, 0x04000000 selection, 0x02000000 et 0x01000000 combat — deux bits par groupe (_INT / _DSP). Hors groupe (pendant OVER par exemple) le sous-etat ne veut rien dire, et la routine ne l'affiche pas.

**Le trio `0x00102010`-`0x00102012` n'est PAS la machine a etats.** Il porte des valeurs de la bonne plage pendant un combat, ce qui l'avait fait prendre pour suivant/precedent/courant — mais il vaut 106, hors table, des qu'on regarde ailleurs : zero concordance sur 589 releves contre `groupe + sous-etat`. Coincidence, pas mecanisme.

Sequences relevees : attract ADV_SEGA_INT -> ADV_SEGA_DSP -> ADV_MOVIE_INT -> ADV_MOVIE_DSP ; selection SEL_START -> SELECT -> DECIDE_DSP ; combat ROUND_MASK -> ROUND -> SET -> READY -> FIGHT -> JUDGE -> REPLAY -> VIC -> NEXT_PROG_SEL. Outil : `etats.py` (`suivre` pour le journal continu).

**Le drapeau `0x0010000A` est un SEMAPHORE, pas un declencheur — tranche du 2026-08-22, en statique.** Ce ne sont pas une routine mais **deux moities**, et le drapeau les relie : `0x00020A28`-`0x00020A88` = debut de trame (attend le DEC, prend le temps de base, POSE le drapeau a 1, `bnelr` s'il vaut deja 1), 7 appelants (`0x022640`, `0x03F990`, `0x03FA94`, `0x04969C`, `0x052D98`, `0x052E10`, `0x05DC10`) ; `0x00020A8C`-`0x00020CD4` = fin de trame (mesure, AFFICHE, remet le drapeau a 0), **2 appelants, `0x004274` et `0x00444C`, tous deux dans la boucle principale — donc appelee a chaque image, sans condition**. Le `blr` en `0x00020A24` prouve que la premiere moitie commence bien A `0x00020A28`, pas avant.

**Ce n'est pas un journal de modes, c'est l'overlay de mise au point de Sega** : sept lignes via le printf maison `0x00035A2C` — `POWER:%5d` (0x8A0A4), `FALSE:` (0x8A0AF), ` POLY:` (0x8A0BA), `   GP:` (0x8A0C5), `   DP:` (0x8A0D0), `ROcal:` (0x8A0E2), puis deux `%-11.11s` (0x8A0ED, 0x8A105) = le mode et le sous-etat, exactement ce que `etats.py` reconstitue de l'exterieur.

**L'interrupteur : bit `0x00400000` du mot `0x00102400`**, teste en `0x00020B18` (`rlwinm. r0,r3,9,0,0` puis `beq`). Il est **recalcule a chaque image** par le gestionnaire de touches de debug `0x00004828` (appele depuis `0x000042EC`), qui l'EFFACE d'abord (`and` 0xF4BFFFFF en `0x0000484C`) : l'ecrire depuis mem.py ne tiendrait pas une image. Il est repose si (1) le bit `0x00200000` du meme mot est arme (remanent) et (2) l'octet `0x001000E0` a les bits `0x80` ET `0x40` (`0x00004860`-`0x00004874`). Cet octet a une seule ecriture, `0x000024BC` : c'est le port materiel **`0xF0040018`** complemente. **Supermodel renvoie 0x7F** (`CModel3::ReadInputs`, `case 0x18`), donc 0x80 seul — le bit 0x40 n'existe pas sous emulateur. Deux sorties : renvoyer `0x3F` pour vf3* dans le fork (garder la garde sur le nom : le commentaire dit qu'Ocean Hunter depend de cette valeur), ou un octet en ROM, **`0x0000486E` / CROM `0x0011486E` / ROM `0xFFF1486E`, `C8` -> `C0`** (SH 25 -> 24 : le second test porte alors sur le meme bit que le premier).

**La manipulation qui arme le mode debug (bit `0x00200000`)** : une seule ecriture, `0x0002B400`, au bout d'un detecteur de sequence a **13 pas** en `0x0002B388` (table de 13 octets en `0x0007CE08` = numeros de bit PowerPC, compteur `0x0010607F`). **LE DESSIN 2D : cartographie faite, mais RIEN NE S'AFFICHE ENCORE (2026-08-22).** Resultat PARTIEL, a ne pas prendre pour une porte ouverte. Le generateur de tuiles est en `0xF1000000` (registres `0xF1180000`) ; en cherchant les `lis` vers cet espace on tombe sur `0x00038700`, qui construit (via `0x00036C58`) **quatre surfaces**, une par couche : objets **`0x0016118C + n*0x2C`**, chacune avec table de noms VRAM `0xF10F8000 + n*0x2000`, **copie en RAM principale `0x00169000 + n*0x2000`**, registre `0xF1180060 + n*4`, motifs `0xF10F6000 + n*0x400`. Champs releves en direct : `+0x08` = 0x40x0x40 (table 64x64), `+0x0C` = 0x3Ex0x30 (fenetre visible 62x48 = 496x384 px), `+0x10` = la copie RAM (base du graveur), `+0x14` = la VRAM, `+0x24/+0x26` = drapeau "a recopier", `+0x00` et `+0x28` = deux vtables.

Encodage, par le graveur de caracteres `0x00036644` : une tuile = **2 octets**, une ligne = **`0x80`** (64 tuiles), numero de tuile = ASCII sur 7 bits, couleur en ajoutant 0x80/0x100. La copie `0x00036CC8` ne part que si le bit 0 de `+0x26` est pose, puis recopie 0x800 mots **en sautant ceux dont les deux tuiles portent `0x8000`** (table compagnon `0x00138FFC`) : **`0x8000` encode le VIDE**, pas une couleur.

ECHEC A NE PAS REFAIRE TEL QUEL : ecrire dans la copie RAM n'affiche rien. Essaye avec trois encodages (ASCII nu, +0x80, +0x100), quatre rangees, avec et sans armer le bit de recopie, police chargee et non. Les octets restent en RAM (relus intacts), l'ecran ne bouge pas. Deux pieges identifies au passage : le premier essai recopiait `0x8020` (l'attribut de la ligne vide) donc ecrivait « rien » soigneusement ; et deux essais sont tombes sur les lignes 1-5 et 21-23, que l'overlay de Sega redessine a chaque image. **Hypothese restante, la plus probable : la copie RAM est la SORTIE d'une liste de plus haut niveau regeneree a chaque image ; la vraie liste d'affichage est un cran au-dessus.**
